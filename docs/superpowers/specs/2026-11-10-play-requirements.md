# Google Play requirements for Wristline (research date 2026-11-10)
Official = support.google.com / developer.android.com. [3P] = third-party only.

## 1. Developer account
- Fee: US$25 one-time; no prepaid cards. Fee not refunded if ID judged invalid. Gov ID + credit card in legal name may be requested. https://support.google.com/googleplay/android-developer/answer/6112435
- Personal accounts only: verify access to an Android device via Play Console mobile app before publishing; must complete app testing requirements. Same page.
- Personal vs org: same core functionality. Org needs D-U-N-S (free from D&B; beware paid middlemen) and is mandatory for finance/health/VpnService/government apps. https://support.google.com/googleplay/android-developer/answer/13634885
- Displayed info: developer name shown. Org: developer email/phone shown publicly (OTP-verified); org name/address/D-U-N-S from payments profile. Personal: page wording unclear whether contact phone/email are public; full address shown for merchant (paid/payments-profile) accounts. Free app = non-merchant, so address likely not shown (my inference, confirm in Console). https://support.google.com/googleplay/android-developer/answer/13634081
- Verification duration: no official figure. [3P] estimates 2-5 business days. https://testerbee.com/blog/google-play-console-registration-fee-and-verification-time
- Closed testing: STILL 12 testers, 14 continuous days, for personal accounts created after 2023-11-13 (cut from 20 to 12 on 2024-12-11, [3P]). Testers who opt out before 14 days don't count; rejoin must still total consecutive 14 days. Production and pre-registration locked until then. Then Dashboard -> "Apply for production" (3 sections: closed test, app, production readiness). Review usually <=7 days; may be told to continue testing (too few testers/low engagement). Internal testing optional; open testing needs production access. https://support.google.com/googleplay/android-developer/answer/14151465
- No 2026 change found to the 12/14 rule. https://www.testerscommunity.com/blog/google-play-closed-testing-requirements-2026 [3P]
- Org account is exempt from closed test ([3P]; official page doesn't state exemption). Choosing org needs D-U-N-S, which a pure individual typically lacks.
- NEW, relevant to sideloaded APKs: Android developer verification. From 2026-09-30 enforced in Indonesia, Singapore, Thailand (+Brazil per some sources); global on certified devices in 2027. Page doesn't mention Italy/EU. Full account $25; free "limited distribution" account (no ID, up to 20 devices, hobbyists). Sideloading stays possible (advanced flow). Google Play registering package names via Play Console counts. https://support.google.com/android-developer-console/answer/16561738 ; https://support.google.com/googleplay/android-developer/answer/10788890
  Implication: publishing on Play likely also covers verification of app.wristline; GitHub APKs signed with same key benefit once package is registered/claimed (confirm in Console).

## 2. Play App Signing with existing key
- Yes allowed for NEW apps: on Play app signing page ("Protected with Play > Play Store protection > Manage Play app signing" / Release > Setup > App signing) click "Change key", choose reuse key from another app or "provide a copy of your own key"; use PEPK tool (download, follow steps) to encrypt and upload. Must be done BEFORE a release reaches open testing/production (closed/internal OK). https://support.google.com/googleplay/android-developer/answer/9842756
- Key requirements: RSA >= 2048 bits; Google-generated default is RSA 4096. Upload key (separate, JKS/keystore, RSA>=2048) recommended different from signing key; may reuse same key as upload key. Same page.
- Caveat: new apps are auto-enrolled in quantum-ready hybrid signing with Google-generated keys; page does not say whether custom key is compatible, and v4 signature scheme not used with hybrid. Verify in Console that "Change key" is still offered; if hybrid forces Google key, Play installs would NOT match the sideloaded signature. Same page; background https://blog.google/security/security-for-the-quantum-era-implementing-post-quantum-cryptography-in-android/
- Phone and watch must use same package name AND same app signing key (WO-G7). https://developer.android.com/docs/quality-guidelines/wear-app-quality
- Practical: Play re-signs delivered APKs with the signing key; uploaded bundle is signed with upload key. Test with internal track first, compare `apksigner verify --print-certs` fingerprint of Play-installed APK to GitHub APK.

## 3. Wear OS
- Same package name; same listing recommended. Console: Test and release > Advanced settings > Form factors > Add form factor > Wear OS; add Wear screenshots. Wear OS APK/bundle is uploaded separately and updated independently; use a dedicated Wear OS release track. Unique versionCode across form factors (your phone+1000 scheme OK, just keep unique and monotonic). https://developer.android.com/distribute/best-practices/launch/distribute-wear ; https://developer.android.com/training/wearables/packaging
- Manifest: `<uses-feature android:name="android.hardware.type.watch" />` (never required=false), and `com.google.android.wearable.standalone` meta-data true/false (non-standalone OK; still installable, needs companion). Same pages.
- Flow: release on closed-test track, opt in to Wear OS in Advanced settings + accept review policy, then Start rollout; review status Pending/Approved/Not approved shown on Pricing and distribution > Wear OS; rejection emailed. No official review duration. Same pages.
- Quality rejection reasons (official): no Wear screenshot; broken functionality/inaccurate screenshots; not formatted for round displays; missing functional requirements (notifications, RemoteInput for messaging). Listing must mention Wear OS per packaging page, but quality page says WO-G2 "mention Wear OS" requirement was REMOVED 2026-03-12 (mention tiles/complications if present; don't say "Android Wear"). Other checks: touch targets 48dp, fonts >=12sp/10sp, black background, swipe-to-dismiss, splash 48dp icon, >=192dp circle, scrollbar, state preservation. WO-P5: non-standalone app's companion must connect and work. https://developer.android.com/docs/quality-guidelines/wear-app-quality
- 64-bit: from 2026-09-15 all Wear OS apps must support 64-bit (check no 32-bit-only native libs). Same page.
- Watch review failure can block listing updates for other form factors; remedy: replace watch artifact with empty submission. Same page FAQ.
- Bundle: docs only say "APK" for watch; Play requires AAB for new apps generally [from my knowledge; not re-verified this session]. Phone+watch together: docs say "multi-APK delivery"; in practice upload an AAB per form factor in own track.
- User install: from watch Play Store directly, or remotely from phone/desktop Play Store ("install on more devices" / watch list). https://developer.android.com/distribute/best-practices/launch/distribute-wear ; https://support.google.com/googleplay/answer/7314788
- RemoteActivityHelper: official example uses ACTION_VIEW + CATEGORY_BROWSABLE with an https://play.google.com/store/apps/details?id=... URI and startRemoteActivity(intent, nodeId); check availability via PlayStoreAvailability. Not confirmed that market:// works via the helper; reported silent failure on Wear OS 4 emulator ([3P] coderapp). Prefer https URL, test on real watch. https://developer.android.com/reference/androidx/wear/remote/interactions/RemoteActivityHelper

## 4. Sensitive permissions / API level
- Notification listener: NO notification-listener-specific policy or declaration form found in official Play pages searched. Applies instead: User Data policy prominent disclosure + consent (in-app, before enabling, affirmative action, not only in privacy policy; exemption only when data use is within functionality prominently described in listing/UI). Recommend prominent in-app disclosure + listing text. https://support.google.com/googleplay/android-developer/answer/11150561 ; policy https://support.google.com/googleplay/android-developer/answer/18258653 (page is 294k chars; only first 100k read, so sections beyond not checked - residual risk).
- Permissions Declaration Form (goo.gle/play-permission-decl-form) required for: SMS/Call Log, QUERY_ALL_PACKAGES, MANAGE_EXTERNAL_STORAGE, photo/video, REQUEST_INSTALL_PACKAGES, USE_EXACT_ALARM, full-screen intent (API 34+), background location, accessibility API. NOT listed: NotificationListener, SYSTEM_ALERT_WINDOW, CALL_PHONE (CALL_PHONE is not a call-log permission), MANAGE_OWN_CALLS, READ_CONTACTS (currently). https://support.google.com/googleplay/android-developer/answer/9888170
- SYSTEM_ALERT_WINDOW: special permission; direct user to system settings page, no runtime prompt. No declaration found. Same page. Be ready to justify core function if reviewers ask.
- READ_CONTACTS: NEW policy. Apps targeting Android 17 / API 37+ may request it only if Contact Picker can't support core functionality; declaration required; Play Console prompts from Sept 2026; compliance mandatory 2027-01-27 (30-day self-extension). Wristline targets 36 so not in scope now, but it WILL apply when you move to API 37 (likely required Aug 2027). Core functionality (resolving caller to contact names for watch) must be justified; custom picker doesn't qualify. https://support.google.com/googleplay/android-developer/answer/16935362 ; some sources cite Jan 27 2027, a June newsletter quote says Oct 28 2026 [3P: capgo.app/blog/google-play-contacts-permission-policy-capacitor/]. Manage Contacts permission: Aug 25 2027.
- Target API: since 2026-08-31 new apps/updates must target API 36+; Wear OS apps API 35+; extension to 2026-11-01 now expired. API 37 expected ~Aug 2027. https://developer.android.com/google/play/requirements/target-sdk
- Full-screen intent: on Android 14+ auto-granted only for alarm/calling apps; relevant if you use USE_FULL_SCREEN_INTENT for call UI. https://support.google.com/googleplay/android-developer/answer/9888170
- Not searched/verified: any Play policy for self-managed ConnectionService (MANAGE_OWN_CALLS) - none found.

## 5. Data safety
- "Collect" = transmit off the device. On-device-only processing is not collection. Collection/sharing questions are about data leaving device to you or third parties. Contacts type includes names, call history. https://support.google.com/googleplay/android-developer/answer/10787469
- Official page does NOT explicitly cover phone -> user's own watch transfers; closest are user-initiated-action exemption and E2E-encryption exemption. Data Layer sync stays between the user's own paired devices (Bluetooth/Wi-Fi) and nothing reaches you or a third party, so reasonable answer: no data collected, no data shared. Judgement call [mine], not official. Conservative alternative: none needed since no developer/third-party access.
- Must still complete form, answer deletion question, and link a privacy policy URL even with no data collected. Same page.
- Local call history/contacts: on-device only -> not declared. No INTERNET permission supports this. Privacy policy should still state what's read (notifications, contacts) and that it stays on device/watch.

## 6. PolyForm Noncommercial
- No Play policy restricting license of an app was found; Developer Program Policy contains no open-source licence requirement in the portion read (first ~100k of 294k chars). Free app, no monetization = consistent. Check: don't include code under licenses incompatible; PolyForm NC is source-available, not OSI "open source" - avoid calling it "open source" in the listing. Low risk. https://support.google.com/googleplay/android-developer/answer/18258653

## 7. Other first-submission gotchas
- Screenshots: phone min 2, max 8/device type; JPEG or 24-bit PNG; each side 320-3840 px, long side <= 2x short; recommended >=4 at 1080px min, 16:9 / 9:16. Wear OS: >=1, 1:1, min 384x384, no device frames/text/transparency. Icon 512x512 32-bit PNG <=1024 KB; feature graphic 1024x500; short description 80 chars. https://support.google.com/googleplay/android-developer/answer/9866151
- Privacy policy URL required (Data safety + app content). Account deletion: only applies if account creation exists; none here -> out of scope; still answer deletion questions. https://support.google.com/googleplay/android-developer/answer/13327111
- App content questionnaire items (from my general knowledge, not fetched): ads declaration (No), content rating IARC, target audience, government app, financial features, health, data safety, Advertising ID declaration (required for API 33+ manifest; if app doesn't use ad ID, declare "No"), news app, app access (provide instructions since features need other apps/permissions).
- Pre-launch report runs on closed track; app access instructions: reviewers can't use WhatsApp calls -> give clear description/video of how to test; consider short demo video of notification-listener use.
- Wear OS review can block listing updates (see 3). Keep Wear OS 64-bit and quality items clean.
- Developer verification (see 1) and contacts policy (see 4) are the two 2026-2027 changes most likely to bite.
- Closed-test planning: need 12 real testers for 14 days AFTER app setup complete; budget ~3-4 weeks incl. production review (<=7 days) plus account verification.
